First, let's meet the three primitives that make this workflow possible.

Primitive 01

Xano CLI

Your terminal interface to Xano — move a whole workspace between Xano and your filesystem, and drive the sandbox.

Pull a workspace

Bring your backend down to local .xs files you can edit and commit.

Push a workspace

Sync local changes back up to a Xano branch when you're ready.

Create a sandbox

Spin up an isolated sandbox workspace that can't touch production.

Push to sandbox

Deploy your change into the sandbox so tests can run against it.

Primitive 02

Xano Developer MCP

Teaches your AI agent how Xano actually works — so it writes valid XanoScript and drives the CLI correctly, instead of guessing.

XanoScript syntax

Documentation on the XanoScript language so the agent writes correct logic.

Validate XanoScript

A tool that checks XanoScript is valid before it ever reaches the sandbox.

CLI guidance

Docs on the CLI so the agent knows how to pull, push, and manage sandboxes.

The MCP turns an agent from "vaguely aware of Xano" into a reliable pair-developer for this workflow.

Primitive 03

Git & GitHub Actions

Your source of truth and your automation engine — changes are managed as PRs in GitHub, not inside the Xano platform.

Version control

Every backend change lives in Git as reviewable, revertible commits.

Pull requests

Manage and review changes through GitHub PRs — the team's familiar flow.

GitHub Actions

Workflows reset the sandbox, push your code, and run tests automatically.

Gated promotion

Real branches update only after the sandbox gate goes green.

The three, together

One workflow, three primitives

Each tool owns a part of the loop — and they hand off to each other cleanly.

Xano CLI

Moves code between Xano and your machine, and drives the sandbox.

Developer MCP

Keeps the agent fluent in XanoScript and the CLI.

Git & GitHub

Manages PRs and runs the sandbox-gated CI/CD.
